# Design

## Context

Мотивация — см. proposal.md, требования — см. specs/user-auth/spec.md. Сейчас `app/routes/api.auth.login.ts` валидирует `{ username, password }` и пишет `username` в подписанную cookie-сессию из `app/sessions.server.ts` (`createCookieSessionStorage`, `SESSION_SECRET`). Внешний сервис на `localhost:3032` (Express) проверен вручную: на неверные данные отвечает `401 {"error":"Invalid login or password"}`, на пустое тело — `400 {"error":"login and password are required"}`. На тестовые данные `test`/`test` сервис отвечает `200` с телом ровно `{ accessToken, refreshToken }`. Оба токена — строки в формате JWT, состоящие только из URL-безопасных символов.

## Goals / Non-Goals

**Goals:**
- Серверное проксирование логина во внешний сервис и сохранение токенов в httpOnly cookie.

**Non-Goals:**
- Refresh-поток, logout, чтение токенов на других маршрутах, удаление старой `__session` у существующих пользователей (cookie просто перестанет обновляться).

## Decisions

- **Вызов только с сервера** (из `action`), а не из браузера: так токены не попадают в JS, а CORS к `localhost:3032` не нужен.
- **Конфигурация:** `AUTH_API_URL` из `process.env`, по умолчанию `http://localhost:3032`. Адрес читается в серверном модуле `app/auth-api.server.ts`, где лежит функция `loginWithAuthApi(login, password)`. Она возвращает размеченный результат: `{ type: "success", tokens } | { type: "invalid", error } | { type: "unavailable" }`. Маршрут только переводит его в HTTP-ответ.
- **Без таймаута и прочего hardening:** проект учебный, код держим минимальным. Зависший сервис задержит ответ — приемлемо.
- **Cookie:** две cookie `accessToken` и `refreshToken` с атрибутами `Path=/; HttpOnly; SameSite=Lax`, плюс `Secure` в production, без `Max-Age`/`Expires` и без подписи. Значение — сам токен, пропущенный через `encodeURIComponent`. Неподписанные — потому что выбраны отдельные cookie, которые могут читать другие сервисы по имени. Без срока жизни cookie живут до закрытия браузера («токены сессии»). Ответ собирается через `Headers` с двумя `append("Set-Cookie", …)`.
  - `Set-Cookie` формирует небольшая функция в `app/auth-cookies.server.ts`, а не `createCookie` из `react-router`: тот всегда кодирует значение как base64(JSON) (`encodeCookieValue` → `encodeData`), и в cookie лежал бы не токен. Альтернатива — пакет `cookie` — отклонена: он есть только как транзитивная зависимость `express`, а добавлять прямую зависимость ради одной строки избыточно.
- **Маппинг ошибок:** `400/401/403` от сервиса → наш `401` с текстом `error` из ответа сервиса, если это строка, иначе «Неверный логин или пароль». Валидация на нашей стороне уже отсекает пустые поля, поэтому `400` от сервиса значит «данные не приняты». Всё остальное (сеть, `5xx`, `2xx` без токенов, не-JSON) → `502` «Сервис авторизации недоступен».
- **Удаление `sessions.server.ts`** вместе с `SESSION_SECRET`: после смены хранения он больше нигде не используется.

## Risks / Trade-offs

- [Неподписанные cookie можно подменить на клиенте] → значение — токен, который проверяет сам сервис авторизации; подмена даёт лишь невалидный токен.
- [Сервис может поменять формат ответа] → код строго проверяет наличие строковых `accessToken`/`refreshToken` и иначе отдаёт `502`. Успешный вход проверяется на тестовых данных `test`/`test`.
- [Сессионные cookie теряются при закрытии браузера] → осознанный выбор по формулировке «токены сессии». Срок жизни можно добавить позже, когда будет известен TTL токенов.

## Migration Plan

Задеплоить с `AUTH_API_URL`, указывающим на сервис авторизации. `SESSION_SECRET` можно убрать из окружения. Откат — revert коммита.
